RAPIDS SQL Metrics 指南

这份文档由最新 NVIDIA/cudf-spark main 分支代码扫描生成，用于解释 Spark event log / Spark SQL UI 中 RAPIDS SQL metrics 的含义、代码位置和性能瓶颈分析方法。

重要: Spark UI 里的 total/min/med/max 是跨 task 聚合后的展示，不是代码里的新 metric。比如 aggregation time total 对应代码里的 aggregation time；aggregation time (excl. SemWait) 是 DEBUG 下自动生成的 companion metric。
诊断配置: 建议采集配置：spark.rapids.sql.metrics.level=DEBUG；新的 op time tracking 由 spark.rapids.sql.exec.opTimeTrackingRDD.enabled 控制并默认开启。
为什么 DEBUG eventlog 仍然不显示某些 metrics？ DEBUG 只是允许 metric 创建和 companion metric 上报；实际是否显示还取决于算子是否在 plan 中、文件格式/reader path 是否适用、对应代码路径是否执行、metric 是否被更新为非零。比如 GpuHashAggregate 没走 sort-based 路径时，sort time 和 sort time (excl. SemWait) 可能不会显示。
为什么 raw total 和 excl. SemWait total 会差很多？ 例如 Spark UI 里 scan time total = 5.80h，而 scan time (excl. SemWait) total = 15.4min，通常说明大部分 raw scan time 是 GPU semaphore 排队时间。客户应该优先看 excl. SemWait 判断 scan 本身工作量，再结合 gpuSemaphoreWait 判断并发/资源配置。

使用限制和代码依据

  • CPU fallback 算子没有 RAPIDS operator timing；需要看 explain/fallback reason、Spark task CPU time 或 CPU profiling。
  • 父子算子的 timing window 可能重叠，不能把所有 visible metrics 无脑相加。
  • 缺少 (excl. SemWait) 通常说明 metrics level 不是 DEBUG。
  • driver-side metrics 来自 SparkListenerDriverAccumUpdates，task-side metrics 来自 SparkListenerTaskEnd。
  • nsTiming 是纳秒；Spark timing 常是毫秒。
  • gpuSemaphoreWait 是 GPU permit 排队时间，需要和 op time (excl. SemWait) 一起看。

代码依据: companion metrics, GpuOpTimeTrackingRDD, wrapWithTimeTrackingRDD, metrics level.

Eventlog 统计方法

  1. 读取 SparkListenerSQLExecutionStart.sparkPlanInfo，建立 accumulator id 到算子和 metric 的映射。
  2. 读取 SparkListenerTaskEnd 中每个 task 的 Accumulables.Update 并按 accumulator id 聚合。
  3. 读取 SparkListenerDriverAccumUpdates 获取 driver-side metrics，例如 metadata 和 commit 统计。
  4. 单独解析 gpuSemaphoreWait，并生成 raw op time 与 excl. SemWait + SemWait 两个视图。
